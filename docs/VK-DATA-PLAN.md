# VK data plan — холодная проверка рынка

Дата: 2026-09-16.

Цель: не выбирать аудиторию, тему и механику по ощущениям. Сначала собрать максимум доступных данных из VK API и публичного каталога, затем принять продуктовые решения.

## 1. Что можно получить напрямую из VK API

### apps.getCatalog

Ключевой метод для каталога игр.

Что важно собирать:
- id приложения;
- title;
- genre / category;
- MAU, если возвращается в extended=1;
- catalog_position;
- screenshots;
- metadata приложения;
- результаты для разных sort;
- результаты по q и genre_id;
- принадлежность к new/recommended/featured, если метод это возвращает.

Отдельные снимки каталога нужны для:
- popular_today;
- popular_week;
- visitors;
- growth_rate;
- create_date;
- popular;
- relevant genres;
- relevant search queries.

Важно: один снимок — это только состояние на момент запроса. Для трендов нужны повторные снимки во времени.

## 2. Панель конкурентов

Собрать отдельный список по механикам:
- Arrow / Tap Away;
- Sort;
- Screw;
- Bubble;
- Match-3;
- Merge;
- puzzle с meta progression;
- puzzle + combat / roguelite, если найдутся.

Для каждой игры хранить агрегат:
- app_id;
- название;
- жанр;
- MAU;
- catalog_position;
- позиции в разных sort/genres;
- сколько раз игра появляется в разных подборках;
- наличие community;
- размер community;
- визуальная упаковка;
- ключевая механика;
- meta layer;
- тема.

## 3. Аудитория через сообщества игр

VK API не следует считать источником точного пола/возраста игроков конкурирующей игры, если сам метод этого не даёт.

Но у многих игр есть официальные сообщества. Для них можно использовать groups.getMembers и агрегировать публичные поля:
- sex;
- bdate;
- city;
- country;
- last_seen, если доступно;
- другие допустимые публичные поля только при реальной необходимости.

Это ПРОКСИ, а не игроки игры.

Нужно считать по каждому сообществу:
- долю мужчин/женщин/не указан;
- возрастные корзины 13–17, 18–24, 25–34, 35–44, 45–54, 55+;
- долю пользователей с известным годом рождения;
- крупные города/страны;
- размер выборки;
- долю закрытых/неполных профилей, если это можно определить корректно.

Нельзя смешивать «подписчики сообщества» и «игроки» в один показатель.

## 4. Сравнение тем

Сегментировать конкурентов по теме, а не только по механике:
- romance / love / Cupid;
- magic / fairy / fantasy;
- treasure / adventure;
- cute animals;
- monsters / combat;
- home / renovation;
- food / household;
- abstract / blocks / arrows.

Для каждой темы сравнить:
- число игр;
- медианный MAU;
- верхний квартиль MAU;
- медианную catalog_position;
- долю игр в popular/growth/new;
- демографию официальных сообществ, если она доступна;
- визуальные повторяющиеся приёмы.

Нельзя делать вывод «тема X лучше» только по одной крупной старой игре.

## 5. Главное исследование для Arrow Roguelite

Нужны ответы на конкретные вопросы:

1. Кто играет в наиболее близкие Arrow / Tap Away игры?
2. Есть ли половой/возрастной перекос у их официальных сообществ?
3. Какие темы puzzle в VK имеют высокий MAU у 25–44 / 35–54 прокси-аудиторий?
4. Combat/fantasy действительно связан с более мужской аудиторией или это предположение?
5. Romance/cute/home действительно связан с более женской аудиторией или это предположение?
6. Есть ли нейтральные темы с хорошими показателями у обоих полов?
7. Как различаются MAU и каталоговые позиции у чистого puzzle и puzzle с meta progression?
8. Насколько новые игры способны быстро попасть в growth/popular без большого накопленного MAU?

## 6. Временной ряд

Если API позволяет стабильно получать данные, сделать ежедневный snapshot хотя бы 7–14 дней.

Хранить:
- timestamp;
- app_id;
- MAU;
- catalog_position;
- sort/list;
- rank внутри конкретной выдачи.

Производные показатели:
- rank_delta_1d;
- rank_delta_7d;
- MAU_delta, если MAU меняется достаточно быстро;
- число появлений в разных выдачах;
- стабильность позиции.

Это важнее одного сегодняшнего скриншота.

## 7. Что НЕ считать доказательством

- число участников сообщества != число игроков;
- пол/возраст подписчиков сообщества != точная демография игроков;
- MAU != DAU и != retention;
- высокая catalog_position не доказывает качество gameplay;
- старая игра с огромной накопленной базой не равна новой игре с текущим органическим ростом;
- отсутствие публичного поля не нужно заменять выдуманной оценкой.

## 8. Технические правила для агента

- токены VK хранить только в ENV / локальном secret store;
- никогда не коммитить access token в git;
- сырой ответ API можно хранить локально, но в репозиторий лучше класть агрегаты и воспроизводимые скрипты;
- не хранить в git массивы user_id без необходимости;
- для демографии сохранять агрегаты, а не профили пользователей;
- логировать endpoint, параметры, время запроса, версию API и ошибки;
- уважать rate limits и Terms of Service;
- при недоступном поле писать unavailable, а не строить число из догадок.

## 9. Предлагаемый результат первой разведки

Агент должен создать локально / в отдельной ветке:

- `data/apps_catalog.csv` — агрегат каталога;
- `data/competitors.csv` — выбранные конкуренты;
- `data/community_demographics.csv` — только агрегированная демография;
- `data/topic_summary.csv` — тема × метрики;
- `reports/VK-MARKET-REPORT.md` — выводы с методикой и ограничениями;
- скрипты сбора, чтобы исследование можно было повторить через неделю.

## 10. Решения после данных

До получения этой выборки не фиксировать:
- целевой пол;
- основной возраст;
- monsters vs Cupid vs treasure;
- глубину roguelite;
- визуальный стиль;
- monetization pressure.

После сбора данных отделить:
1. факты VK API;
2. прокси по игровым сообществам;
3. ручные наблюдения;
4. продуктовые гипотезы.
