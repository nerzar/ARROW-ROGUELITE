## Текущий этап

Проект вышел из чистой фазы исследования в **product design + technical spike**.

Мы всё ещё не считаем production-MVP запущенным. Сейчас параллельно:

- продолжаем анализ VK Games и рынка;
- уточняем аудиторию/тему;
- фиксируем игровой концепт;
- проектируем первый run и content system;
- исследуем готовые Arrow generator/solver наработки;
- делаем технический spike puzzle-core, чтобы доказать жизнеспособность generator + solver + difficulty model до production-разработки.

Каноническая короткая точка входа в игру: `docs/GAME-CONCEPT.md`.

## Игровое ядро — текущий контекст

AGREED FOR NOW:

- основа — Arrow/Tap Away puzzle;
- освобождённая стрелка не исчезает, а становится projectile во внешней арене;
- внешние цели находятся по сторонам board;
- направление позже становится боевым ресурсом;
- это впервые явно раскрывается на mini-boss в конце пролога;
- там же игрок впервые получает Rotate;
- boss rewards должны менять правила/поведение стрел, а не только цифры;
- data-driven content предпочтительнее hardcoded контента;
- позднее допускается управляемый power-gating: не каждый encounter обязан проходиться базовым набором без run/meta-power или помощи.

Подробности и границы гипотез — в `docs/GAME-CONCEPT.md`.

## Проверка

Пока production stack не выбран, общие проверки задаются в каждой task-карточке.

Для game/core spike минимум:

- не смешивать renderer с чистой puzzle-логикой без необходимости;
- generator должен быть deterministic/reproducible;
- solvability должна проверяться кодом, а не предположением агента;
- property/seed tests обязательны для generator/solver;
- чужой код использовать только при подтверждённой лицензии; reference-only проекты не копировать;
- не превращать spike-решение автоматически в production architecture.

Для VK research-задач минимум:

- не раскрывать `VK_SERVICE_TOKEN`;
- `.env` и raw artifacts не должны попадать в Git;
- API collector должен быть воспроизводимым;
- фактические поля API важнее предположений из документации;
- итоговые публичные данные должны быть агрегированными там, где работа касается пользовательской демографии.

## Что особенно дорого

- генерация большого количества уникальных изображений;
- дорогие модели без необходимости;
- повторное исследование уже собранных данных;
- массовые API-запросы без плана и снапшотов;
- чтение всего репозитория каждым новым агентом;
- несколько агентов, делающих одну и ту же работу;
- production-код до проверки ключевой механики.

Распределение моделей:

- Claude Opus/Sonnet — важные архитектурные, продуктовые и сложные технические задачи;
- Muse Spark — дешёвый разбор больших объёмов контекста/данных и хорошо ограниченные механические задачи;
- сильную модель не тратить на чтение десятков мегабайт, если можно сначала отфильтровать кандидатов дешёвым агентом.
