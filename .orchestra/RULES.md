# Общие правила

Этот файл хранит общие правила работы. Git-процесс — в `GIT.md`, текущее состояние проекта — в `PROJECT.md`, активная работа — в `BOARD.md`.

## Главный принцип

Используем минимально достаточную модель и минимально достаточный контекст, но не экономим в ущерб результату.

По умолчанию предпочитаем **сделать рабочий результат**, показать его пользователю и получить обратную связь, а не строить вокруг задачи дополнительные слои анализа.

Не запускать несколько агентов на одну простую задачу без причины. Не перечитывать весь репозиторий, если достаточно task-card и нескольких нужных файлов. Не повторять исследование, уже сохранённое в Git.

## Кто принимает решения

Проектные, архитектурные, игровые и визуальные решения принимает только пользователь.

AI может предложить, сравнить, проверить и рекомендовать, но не превращает рекомендацию в принятое решение.

Состояния договорённостей:
- `IDEA` — гипотеза;
- `AGREED FOR NOW` — выбранное пока направление, его можно пересмотреть;
- `STRICT RULE` — жёсткое правило, менять только с разрешения пользователя.

## Роли

- Пользователь — владелец проекта и последнее слово.
- Архитектор — держит текущий контекст, формулирует следующий полезный шаг, создаёт task-card и проверяет сдачу.
- Геймдизайнер уровней — подбирает/проверяет board seed'ы и encounter-варианты; финальный выбор и баланс принимает пользователь. Подробности — в `LEVEL-DESIGNER.md`.
- Локальный техлид — следит за процессом на машине пользователя и вмешивается, если исполнитель зациклился, конфликтует с чужой работой или ушёл за рамки.
- Исполнитель — делает одну назначенную задачу, проверяет, сдаёт и останавливается.

## Типы задач

- `EXP` — проверить конкретную неизвестность или вариант.
- `BUILD` — сделать выбранный рабочий результат или инструмент.
- `FIX` — исправить конкретный дефект.
- `REVIEW` — отдельно проверить уже сделанную работу, когда для этого есть реальная причина.

`REVIEW` и отдельный `EXP/research` создаются только при конкретной неопределённости, риске или спорном результате, который нельзя разумно закрыть обычной реализацией и проверкой исполнителя.

Не создавать research/review или второго агента «на всякий случай». Если следующий полезный шаг очевиден — делать его.

## Размер

- `S` — короткая задача, один исполнитель.
- `M` — обычная задача, один исполнитель; допустим один дополнительный круг исправления.
- `L` — действительно сложная/рискованная задача; сильная модель или дополнительные агенты подключаются осознанно.

Исполнитель сам не повышает себе размер задачи и не расширяет scope.

## Контекст исполнителя

Обычно достаточно:
1. `RULES.md`;
2. `PROJECT.md`;
3. `GIT.md`;
4. своей task-card;
5. файлов, прямо нужных для задачи.

`BOARD.md` нужен архитектору как навигация по текущей работе. Исполнителю не нужно читать весь backlog.

**Task-card — основной источник постановки.** Чатовый prompt не должен дублировать её целиком.

Не читать старые DONE task-card, отчёты и design/research документы без конкретной причины. Если прошлый результат действительно нужен, текущая карточка должна явно назвать файл/ветку/commit или кратко перенести нужный факт.

## Каким должен быть task-card

Карточка хранит только то, что нужно исполнителю для этой задачи:
- цель;
- актуальный контекст/входы;
- действительно обязательные ограничения;
- критерии проверки;
- после работы — короткие `RESULT / VERIFY / FOUND`.

Task-card **не является дневником работы**. Не дописывать туда хронологию каждого browser-loop, попытки, промежуточные рассуждения и полный пересказ diff.

После завершения `RESULT` должен описывать финальное состояние, а не историю того, как к нему пришли. `FOUND` — только проблемы/расхождения, которые реально важны для следующего решения.

Если длинное исследование имеет самостоятельную ценность в будущем, вынести его в отдельный документ. Не раздувать каждую task-card ради архива: история уже остаётся в Git.

## Как передавать задачу исполнителю

Обычно достаточно короткого сообщения:

`Возьми TASK <ID> на ветке <branch>. Прочитай orchestra docs и task-card. Новый контекст: <1–3 предложения>. Сделай, проверь и сдай по правилам.`

В prompt не повторять:
- весь Git-процесс;
- стандартный порядок сдачи;
- содержимое `RULES.md`, `PROJECT.md`, `GIT.md`;
- длинный список старых решений;
- конкретный браузер/tool, если это не часть требования.

Prompt несёт только новый контекст, важные именно сейчас ограничения и ожидаемый результат.

Оставлять исполнителю свободу реализации и способа проверки, если конкретный способ не является требованием.

## Рабочий цикл

Нормальный цикл:

`пользователь -> архитектор -> один исполнитель -> проверка -> пользователь/архитектор решает следующий шаг`.

Исполнитель делает короткий recon по нужным файлам и переходит к работе. Исследование перед реализацией нужно только там, где без него действительно нельзя принять техническое решение.

Если задача требует выйти за scope — записать проблему в `FOUND`; не чинить побочно всё найденное и не создавать себе новые задачи.

## Браузер и визуальная проверка

Если задача визуальная или интерактивная, просить проверить результат **в браузере**. Не привязывать постановку к Chrome/Edge/конкретному automation tool без необходимости.

Не запускать повторяющиеся browser-циклы ради формальности. Проверка должна доказать критерии задачи и остановиться.

Автотесты не заменяют человеческую оценку внешнего вида, UX и game feel.

Визуальная работа не считается принятой только потому, что агент написал `DONE` или тесты зелёные. До следующего шага, зависящего от визуального направления, пользователь должен реально увидеть результат и принять/отклонить его.

Для playtest сначала добиваемся читаемого рабочего результата. Финальный арт-полиш — отдельный этап после пользовательского подтверждения направления.

## Экономия токенов

- Не дублировать одну задачу нескольким агентам без причины.
- Не делать отдельный review каждого обычного `S/M` результата.
- Не создавать research-задачу, если гипотезу быстрее проверить кодом/прототипом.
- Не заставлять агента заново собирать контекст, уже сохранённый в текущей task-card или каноническом документе.
- Не требовать длинных отчётов: коротких конкретных `RESULT / VERIFY / FOUND` достаточно.
- Не строить заранее длинную цепочку задач. Следующий шаг определяется после результата и, для визуальной работы, после просмотра пользователем.
