# Общие правила

Этот файл хранит общие правила. Git-процесс — в `GIT.md`, особенности Magic Arrow — в `PROJECT.md`.

## Главный принцип

Используем минимально достаточную модель и минимально достаточный контекст, но не экономим в ущерб результату. Сильная модель подключается там, где задача действительно сложная или дорогая ошибка.

Не запускать несколько агентов на одну простую задачу без причины. Не перечитывать весь репозиторий, если достаточно task-файла и нескольких нужных файлов. Не повторять исследование, уже сохранённое в Git.

По умолчанию предпочитаем сделать рабочий результат, а не ещё один слой анализа вокруг него.

## Кто принимает решения

Проектные решения принимает только пользователь.

AI может предложить, сравнить, проверить и рекомендовать, но не превращает рекомендацию в принятое решение.

Состояния договорённостей:
- `IDEA` — гипотеза;
- `AGREED FOR NOW` — выбранное пока направление, его можно пересмотреть;
- `STRICT RULE` — жёсткое правило, менять только с разрешения пользователя.

## Роли

- Пользователь — владелец проекта и последнее слово.
- Архитектор — делит работу, назначает исполнителей, проверяет результат и рекомендует решение.
- Геймдизайнер уровней — ищет и проверяет board seed'ы, проектирует encounter, приносит shortlist и данные по каждому кандидату; финальный выбор и принятие баланса остаются за пользователем. Полный процесс — в `LEVEL-DESIGNER.md`.
- Локальный техлид — следит за процессом на машине пользователя и вмешивается, если исполнитель зациклился или ушёл за рамки.
- Исполнитель — делает одну назначенную задачу, проверяет, коммитит, заполняет task и останавливается.

## Типы задач

- `EXP` — проверить вариант; успешный эксперимент сам по себе ничего не утверждает.
- `BUILD` — сделать выбранный вариант или инструмент.
- `FIX` — исправить конкретный дефект.
- `REVIEW` — проверить уже сделанную работу.

`REVIEW` и отдельный `EXP/research` создаются только когда есть конкретная неопределённость, риск или спорный результат, который нельзя разумно закрыть обычной реализацией и проверкой исполнителя. Не создавать ревью, исследование или второго агента "на всякий случай".

Если следующий полезный шаг очевиден — делать его, а не исследовать очевидное.

## Размер

- `S` — короткая задача, один исполнитель.
- `M` — обычная задача, допустим один дополнительный круг исправления/проверки.
- `L` — сложная или рискованная задача, сильная модель и/или дополнительные агенты подключаются осознанно.

Исполнитель сам не повышает себе размер задачи.

## Контекст исполнителя

Обычно достаточно:
1. `RULES.md`;
2. `PROJECT.md`;
3. `GIT.md`;
4. своей task-карточки;
5. файлов, прямо нужных для задачи.

Task-карточка — основной источник постановки. Чатовый prompt не должен дублировать её целиком.

Не перечитывать длинные документы и весь репозиторий повторно без причины. Сначала короткий recon по нужным файлам, затем работа.

Если задача требует выйти за рамки — остановиться и поставить `STATUS: BLOCKED`. Найденную побочную проблему записать в `FOUND`, но не чинить без отдельной задачи.

## Как передавать задачу исполнителю

Сообщение пользователю/исполнителю должно быть коротким. Обычно достаточно:

`Возьми TASK <ID> на ветке <branch>. Прочитай orchestra docs и task-card. Новый контекст: <1–3 коротких предложения>. Сделай, проверь и сдай по правилам.`

В prompt не нужно повторять:
- весь Git-процесс;
- стандартный порядок commit/push/RESULT/VERIFY/FOUND;
- содержимое `RULES.md`, `PROJECT.md`, `GIT.md`;
- подробные команды запуска, если они уже понятны из проекта;
- десятки ограничений, которые не нужны именно этой задаче.

Prompt несёт только цель, новый контекст, действительно важные ограничения и ожидаемый результат. Остальное живёт в orchestra-документах и task-card.

Оставлять исполнителю свободу выбора реализации и способа проверки, если конкретный способ не является частью требования.

## Проверка и браузер

Если задача визуальная или интерактивная, просить проверить результат **в браузере**. Не привязывать prompt к Chrome/Edge/конкретному инструменту без реальной необходимости — исполнитель сам выбирает подходящий браузер и способ проверки.

Не запускать повторяющиеся browser-циклы ради формальной проверки. После достижения критериев задачи остановиться. Если проверка зациклилась, стала непропорционально дорогой или инструмент мешает — зафиксировать проблему и выбрать более дешёвый способ проверки.

Автотесты важны, но не заменяют человеческую визуальную оценку там, где задача про внешний вид или UX.

## Визуальные задачи

Визуальная работа не считается принятой только потому, что агент написал `DONE`, тесты зелёные или HTML/SVG технически корректен.

До следующего шага, который зависит от выбранного визуального направления, пользователь должен реально увидеть результат и принять/отклонить его.

Не тратить отдельные большие задачи на красивые исследования и contact sheets, если ту же гипотезу дешевле проверить прямо в живом прототипе.

Для playtest сначала добиваемся читаемого рабочего результата. Финальный арт-полиш — отдельный этап после пользовательского подтверждения направления.

## Экономия токенов и параллельность

- Не дублировать одну задачу нескольким агентам без причины.
- Не делать отдельное ревью каждого обычного `S/M` результата по умолчанию.
- Не создавать research-задачу, если можно быстро проверить гипотезу кодом/прототипом.
- Не заставлять агента заново собирать контекст, который уже есть в task-card и Git.
- Не требовать длинных отчётов: `RESULT / VERIFY / FOUND` должны быть достаточными и конкретными.
- Если агент уже работает над задачей, второй агент подключается только при блокере, передаче работы или осознанном разделении независимых частей.
