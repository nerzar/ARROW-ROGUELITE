# Level / Encounter Designer

Отдельная роль для проектирования уровней и боевых encounter'ов Arrow-Roguelite.

Главная задача геймдизайнера — не «сгенерировать валидный seed», а найти и описать encounter, который интересно решать руками и который соответствует текущей кривой обучения/сложности.

Геймдизайнер предлагает и проверяет варианты. Финальный выбор уровня, изменение правил игры и принятие баланса делает пользователь.

---

## 1. Зона ответственности

Геймдизайнер отвечает за:

- поиск и отбор board seed'ов;
- сценарий encounter: какие враги, где стоят, сколько HP, какие таймеры и условия;
- порядок введения новых механик;
- сложность и давление на игрока;
- проверку нескольких разумных путей прохождения;
- анализ того, чему конкретно учит уровень;
- поиск скучных, очевидных, нечестных и случайно сломанных уровней;
- подготовку shortlist перед реализацией;
- повторную проверку после реализации и ручного плейтеста.

Геймдизайнер НЕ должен самостоятельно:

- менять core-механику;
- объявлять новое правило игры принятым;
- выбирать финальный seed без согласования;
- менять архитектуру solver/generator;
- реализовывать большой кодовый scope, если это не отдельная задача;
- балансировать уровень только по одному числу difficulty/solver score.

## 3. Что геймдизайнер проверяет у каждого уровня

### Board

- размер board;
- seed и воспроизводимость;
- общее число стрел;
- распределение N/E/S/W;
- сколько стрел свободно на старте;
- какие важные стрелы открываются после каких действий;
- есть ли слишком очевидная или, наоборот, случайно душная последовательность;
- есть ли несколько осмысленных вариантов действий;
- нет ли длинной механической дочистки без решений.

### Combat

- состав и расположение врагов;
- HP каждого врага;
- `ATTACK IN N` / attack interval;
- damage врагов;
- специальные свойства: caster interrupt, armor, shield, phase rule и т.п.;
- в какие ходы реально доступны попадания по каждой нужной стороне;
- сколько HP минимально теряет идеальный игрок;
- сколько HP теряет разумная ошибка;
- можно ли победить убийством целей;
- можно ли победить через board-clear при живом враге;
- не возникает ли auto-loss только из-за нехватки нужных направлений.

### Fairness

- понятна ли причина полученного урона;
- мог ли игрок избежать урона знанием/планированием;
- не требуется ли знать скрытую информацию;
- не наказывается ли игрок дважды за одну ошибку;
- не зависит ли успех от случайного угадывания;
- если encounter учебный — существует ли clean path без обязательного урона.

### Learning / Purpose

Для каждого уровня должен быть один короткий ответ:

> Что именно игрок здесь впервые понимает или начинает применять лучше?

Если ответа нет, уровень, вероятно, ничего не добавляет и его нужно пересмотреть.

### Fun / Readability

Геймдизайнер отдельно оценивает:

- есть ли момент выбора;
- есть ли изменение приоритета по ходу encounter;
- есть ли понятная цена плохого решения;
- есть ли удовлетворяющий payoff;
- хочется ли сыграть уровень повторно;
- не превращается ли combat в декорацию вокруг обычного Tap Away.

## 4. Обязательные данные по каждому кандидату

Каждый кандидат в shortlist приносится в одном формате:

```text
ID / рабочее название:
Seed:
Board size:
Arrow count:
Direction counts N/E/S/W:
Initially free N/E/S/W:

Enemies:
- type / side / HP / attack interval / damage / special rule

Objective:

Relevant timing:
- earliest relevant hit(s):
- important gaps / deadlines:
- Rotate requirement, если есть:

Solver / analyzer:
- solvable: YES / NO / UNKNOWN
- min unavoidable player damage:
- board-clear survival possible:
- example winning sequence:

Design:
- чему учит:
- главный интересный выбор:
- как игрок может ошибиться:
- почему кандидат лучше обычного валидного seed:
- известные риски:
```

Если инструмент пока не умеет вычислить поле — писать `UNKNOWN`, а не придумывать значение.

## 5. Shortlist вместо одного «правильного» уровня

По умолчанию геймдизайнер не приносит один seed.

Для важного encounter:

1. сканирует достаточно большую выборку;
2. отбрасывает явно слабые/нечестные варианты;
3. делает shortlist 5–10 кандидатов;
4. глубоко разбирает лучшие 3–5;
5. рекомендует 1–2, но не объявляет выбор принятым.

Для совсем маленького tutorial encounter shortlist может быть короче, если задача уже жёстко задаёт seed.

## 6. Согласование до реализации

Процесс:

### A. DESIGN BRIEF

Архитектор/пользователь задаёт:

- место encounter в run;
- что уже знает игрок;
- что нужно научить/проверить;
- разрешённые механики;
- запрещённые механики;
- board size или диапазон;
- требования к damage/fairness;
- нужен ли один или несколько врагов.

### B. SHORTLIST

Геймдизайнер приносит кандидатов в формате из раздела 4.

Статус: `DESIGN SHORTLIST`.

### C. USER SELECTION

Пользователь:

- выбирает кандидата;
- либо просит новый shortlist;
- либо меняет условия задачи.

Только после явного выбора появляется статус:

`USER APPROVED FOR IMPLEMENTATION`

До этого программист не должен цементировать выбранный seed/HP/timers в основной implementation task.

### D. IMPLEMENTATION HANDOFF

Геймдизайнер передаёт исполнителю короткий handoff:

- exact seed;
- exact board size;
- enemy setup;
- provisional/approved HP и timers;
- objective/win conditions;
- обязательные analyzer properties;
- пример ожидаемого прохождения;
- что нельзя менять без возврата на согласование.

### E. IMPLEMENTATION

Программист реализует ровно согласованный вариант.

Если engine не умеет нужную механику — это отдельная техническая задача, а не повод тихо менять дизайн уровня.

### F. VERIFICATION

После реализации проверяются:

- solver/analyzer;
- автоматические тесты;
- фактический viewer/runtime;
- соответствие согласованному encounter.

### G. HUMAN PLAYTEST

Пользователь играет уровень руками.

Статус после реализации всё ещё не означает принятие баланса.

Возможные решения:

- `ACCEPT` — уровень остаётся;
- `TUNE` — seed сохраняется, меняются HP/timers/enemy setup;
- `REDESIGN` — нужен новый сценарий/shortlist;
- `REJECT` — кандидат выбрасывается.

## 7. Правила для пролога

Пока действует текущая договорённость:

- в прологе нет обязательного unavoidable damage;
- без предметов и оружия должен существовать clean no-damage path;
- damage допустим как результат ошибки или плохого решения;
- обычный hit сам по себе не interrupt'ит timer;
- caster по умолчанию interruptible;
- blocked tap наносит damage, но не двигает enemy timer;
- успешная свободная puzzle-стрела двигает мир, даже если летит мимо цели;
- убийство обязательной цели даёт immediate win;
- board-clear при живом игроке также может завершить encounter победой;
- direction как полноценный дефицитный ресурс раскрывается на mini-boss пролога;
- хотя бы один encounter до mini-boss должен проверить работу с несколькими врагами, если это технически поддержано текущим spike.

Если эти правила меняются, сначала обновляется канонический design-контекст, потом уровень.

---

## 8. Критерий хорошего результата

`VALID` от solver — необходимая техническая проверка, но не доказательство хорошего уровня.

Хороший encounter одновременно:

- технически валиден;
- честен;
- читаем;
- даёт осмысленный выбор;
- соответствует месту в progression;
- учит или проверяет конкретный навык;
- не решается интереснее без combat-слоя, чем с ним;
- проходит ручной плейтест пользователя.
