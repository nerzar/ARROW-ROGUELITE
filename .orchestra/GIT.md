# Работа через Git

Git — общая память проекта и способ передавать работу между агентами.

## Ветки

Долго живёт `main`. Общая integration-ветка пока не зафиксирована; её можно ввести отдельно перед параллельной разработкой игры.

Каждая задача, которая меняет код/настройки/документацию/ассеты, работает в своей ветке:
- `exp/EXP-...`
- `build/BUILD-...`
- `fix/FIX-...`

`REVIEW` без изменений может работать без ветки.

## Кто создаёт задачу

Карточку `.orchestra/tasks/<TASK>.md` создаёт архитектор до передачи работы исполнителю. Исполнитель не создаёт себе новые задачи самостоятельно.

## Перед началом

Исполнитель:
1. `git fetch --all --prune`;
2. читает `RULES.md`, `PROJECT.md`, `GIT.md` и свою карточку;
3. проверяет `BASE_BRANCH` и `START_SHA`;
4. переключается/создаёт указанную task-ветку;
5. не берёт более свежую базу и не делает rebase самовольно.

Если стартовую точку нельзя воспроизвести — `STATUS: BLOCKED`.

## Ограничения исполнителя

Исполнитель меняет только разрешённые task-файлом файлы и свою task-карточку.

Без отдельного разрешения запрещено:
- merge в `main`;
- force push `main` или общей ветки;
- rebase общей ветки;
- переписывание чужих commit;
- большой рефакторинг вне задачи;
- самостоятельное взятие следующей задачи.

## Сдача

Перед `STATUS: DONE` исполнитель ОБЯЗАН по порядку:
1. выполнить указанные проверки;
2. заполнить `RESULT`, `VERIFY`, `FOUND`;
3. сделать code/report commits (финальный commit включительно);
4. `git push origin <task-branch>`;
5. проверить, что `origin/<task-branch>` указывает на ожидаемый `RESULT_SHA`;
6. только после этого поставить `STATUS: DONE` и остановиться.

`DONE` без запушенного на remote `RESULT_SHA` — неправильная сдача: считать задачу не сданной, а исполнителя — не завершившим работу, даже если весь остальной чек-лист выполнен.

`DONE` значит только «исполнитель закончил», а не «работа принята».

Исполнитель НЕ удаляет свою task-ветку до решения пользователя — ни локально, ни на remote. Ветка остаётся нетронутой, пока работу не примут.

Архитектор смотрит task, diff, SHA и проверки и рекомендует `ACCEPT`, `FIX` или `REJECT`. Решение принимает пользователь.

## После решения пользователя

Принятая работа сливается выбранным пользователем/архитектором способом. По умолчанию:
- `BUILD` / `FIX` — `no-ff`;
- принятый `EXP` — squash;
- `REVIEW` без изменений — без merge.

После `ACCEPT` и интеграции архитектор/integrator (не исполнитель задачи):
1. записывает задачу одной строкой в `.orchestra/archive/YYYY-MM.md`;
2. удаляет task-файл `.orchestra/tasks/<TASK>.md`;
3. удаляет task-ветку локально;
4. удаляет task-ветку на remote;
5. удаляет запись с `BOARD.md`;
6. выполняет `git fetch --all --prune`.

`main` — архив результата; старые task-ветки в нём не нужны и не хранятся отдельно от истории `main`. Ветки и task-файлы не используются как вечный архив: полная история остаётся в Git.
