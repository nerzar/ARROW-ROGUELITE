# Работа через Git

Git — общая память проекта и способ безопасно передавать работу между агентами. Но Git history хранит историю; task-card и ветки не должны превращаться в вечный архив.

## Ветки

Долго живёт `main`.

Общая integration-ветка пока не зафиксирована. Текущий playable baseline и активную задачу смотреть в `PROJECT.md` и `BOARD.md`.

Каждая задача, которая меняет код/настройки/документацию/ассеты, работает в своей ветке:
- `exp/EXP-...`
- `build/BUILD-...`
- `fix/FIX-...`
- `docs/...`, `tool/...`, `design/...` — когда тип работы этого требует.

`REVIEW` без изменений может работать без отдельной ветки.

## Worktree / рабочий каталог

Не переключать ветку в рабочем каталоге, которым уже пользуется другой агент, и не трогать checkout с чужими незакоммиченными изменениями.

Если задачи идут параллельно, root checkout занят/грязный или есть риск столкновения — использовать отдельный `git worktree`/рабочую директорию с самого начала.

Если работает один исполнитель в чистом checkout, отдельный worktree не является обязательной церемонией.

## Кто создаёт задачу

Task-card `.orchestra/tasks/<TASK>.md` создаёт архитектор до передачи работы исполнителю. Исполнитель не создаёт себе новые задачи самостоятельно.

Карточка должна быть короткой постановкой текущей задачи, а не пересказом всей истории проекта.

## Перед началом

Исполнитель:
1. делает `git fetch --all --prune`;
2. читает минимальный контекст из `RULES.md`, `PROJECT.md`, `GIT.md` и своей task-card;
3. проверяет `BASE_BRANCH` / `START_SHA`, если они заданы;
4. работает только в назначенной task-ветке/рабочей директории;
5. не подтягивает более свежую базу и не делает rebase самовольно.

Если указанную стартовую точку нельзя воспроизвести — остановиться и сообщить `BLOCKED`, а не импровизировать с другой базой.

## Ограничения исполнителя

Без отдельного разрешения запрещено:
- merge в `main`;
- force push `main` или общей ветки;
- rebase общей/чужой ветки;
- переписывание чужих commits;
- большой рефакторинг вне задачи;
- переключение/ломание checkout другого агента;
- самостоятельное взятие следующей задачи.

По возможности менять только файлы, реально нужные задаче. Жёсткий список allowed files нужен лишь там, где риск scope creep действительно высок.

## Сдача

Перед `STATUS: DONE` исполнитель:
1. выполняет разумные проверки из task-card;
2. приводит `RESULT / VERIFY / FOUND` к короткому финальному виду;
3. коммитит изменения;
4. push'ит task-ветку;
5. убеждается, что нужные commits существуют на `origin/<task-branch>`;
6. ставит `STATUS: DONE`, push'ит финальный report/task commit и останавливается.

`DONE` без push на remote не считается сдачей.

Не нужно заставлять task-card ссылаться на SHA собственного финального commit — это создаёт бессмысленный круг. Если поле `RESULT_SHA` используется, оно может указывать на основной code/result commit; финальный task/report commit может идти следом.

`DONE` означает только «исполнитель закончил». Это не означает, что пользователь принял результат.

Исполнитель не удаляет task-ветку до принятия/интеграции результата.

## Проверка результата

Архитектор проверяет только то, что нужно для решения:
- task-card;
- relevant diff/commits;
- заявленные проверки;
- живой результат, если задача визуальная/интерактивная.

Не создавать отдельный REVIEW автоматически для каждой обычной `S/M` задачи. Второй агент нужен при реальном риске, споре, блокере или дорогой ошибке.

Решение `ACCEPT / FIX / REJECT` принимает пользователь; архитектор может дать рекомендацию.

## После ACCEPT

После принятия и интеграции architect/integrator:
1. добавляет одну короткую строку в `.orchestra/archive/YYYY-MM.md`;
2. удаляет завершённую task-card;
3. удаляет запись с `BOARD.md`;
4. удаляет временную task-ветку локально/на remote, когда она больше не нужна;
5. делает prune.

Не хранить десятки завершённых веток «на всякий случай»: полная история уже есть в Git и в принятой истории целевой ветки.

## Принцип интеграции

По умолчанию:
- принятый `BUILD` / `FIX` — `no-ff`;
- принятый `EXP` — squash, если пользователь не решил иначе;
- `REVIEW` без изменений — без merge.

Не тащить в целевую ветку unrelated task-card, research/design ветки или промежуточные эксперименты только потому, что они случайно присутствуют в ancestry. Интегрировать результат осознанно.
